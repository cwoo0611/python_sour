# 빈집 프로젝트 DB 설계

현재 확보한 데이터로 만든 실행 가능한 SQLite 시제품입니다. SQLite 파일에는 실제 데이터가 적재되어 있습니다. MySQL/MariaDB 전용 SQL은 아니므로 해당 서버에 옮길 때 자료형과 자동 증가 키 문법을 변환해야 합니다.

## 테이블과 적재 결과

| 테이블 | 한 행이 뜻하는 것 | 실제 행 수 |
|---|---|---:|
| data_sources | 수집한 자료와 조회 범위 | 6 |
| raw_records | 가공 전 CSV/API 원본 한 행 | 1,468 |
| regions | 데이터에 등장한 시·군·구 | 4 |
| vacant_houses | 빈집으로 분류된 원본 한 행 | 896 |
| building_registers | 조회된 건축물대장 표제부 | 5 |
| house_building_links | 근거를 확인한 빈집-건축물 연결 | 0 |
| commercial_stores | 상가 업소 | 5 |
| construction_notices | 건설업 등록 공시 | 5 |
| regional_visitor_stats | 지역·날짜·방문자 구분별 집계 | 5 |
| users | 서비스 회원 | 0 |
| saved_houses | 회원이 저장한 빈집과 메모·별점 | 0 |
| business_types | 카페·숙박·음식점·공방·사무실·기타 | 6 |
| saved_house_business_types | 관심 빈집에서 선택한 희망 업종 | 0 |

## 왜 이렇게 나눴는가

`vacant_houses`에는 집 자체의 구조·면적·등급을 넣습니다. `saved_houses`에는 사람마다 달라지는 메모·선호도를 넣습니다. 한 빈집을 여러 사람이 저장해도 빈집 정보를 복제할 필요가 없습니다. `(user_id, house_id)` 중복을 금지해 같은 사람이 같은 빈집을 두 번 저장하지 못하게 했습니다.

희망 업종은 여러 개를 선택할 수 있으므로 연결 테이블을 사용합니다. 예를 들어 같은 저장 항목에 카페와 공방 두 행을 연결합니다. 별점은 1~5 또는 미입력 NULL만 허용합니다. 회원의 비밀번호는 해시값만 저장하며 실제 회원이나 임시 비밀번호를 만들지 않았습니다. 로그인 구현 시 안전한 비밀번호 해시 라이브러리를 사용해야 합니다.

`regions`는 현재 데이터에 필요한 시군구 단계만 구현했습니다. 고창의 읍면 명칭은 원본 `법정동` 값을 `locality_name`에 보존하고, 양산의 읍면동리 표기는 공개 주소에 그대로 남겼습니다. UI의 리·동 단위 지도 집계를 구현할 때는 행정구역 기준표와 주소 정제 후 하위 지역 테이블 및 FK를 추가해야 합니다. 지금 이 DB로 개별 건물 위치나 리별 경계가 완성되었다고 볼 수 없습니다.

상가와 업체를 특정 빈집에 고정 연결하지 않았습니다. 지역별로 조회할 수 있고, 빈집의 정확한 좌표를 확보한 뒤 거리 기반 검색을 추가할 수 있습니다. 키스콘의 `GongsiReg` 결과는 등록 공시이므로 `construction_notices`로 저장했습니다. 현재 영업 중인 전체 업체 명부로 취급하지 않습니다. 향후 업체 대표 테이블을 추가하고 공시 이력을 별도로 연결할 수 있습니다.

건축물대장은 빈집과 별개입니다. 공개 빈집 주소에는 지번 일부가 가려져 있고 건축물대장 샘플에도 지번 0000이 있어 같은 건물인지 확정할 수 없습니다. `house_building_links`는 정확한 주소 등의 확인 근거가 있을 때만 적재하도록 비워뒀습니다.

## 실제 데이터에서 확인한 내용

- 고창 1,288행 중 `빈집판정결과=해당`인 736행만 서비스 빈집으로 넣었습니다. 나머지 552행은 원본 테이블에 보존했습니다. 고창의 등급은 1등급 44건, 2등급 615건, 3등급 77건입니다.
- 양산은 CSV 전체 160행을 넣었습니다. 고창과 양산을 합해 896행입니다. 이는 원본의 빈집 분류 기준에 따른 건수이며 현장 실재 및 거래 가능 여부를 검증한 결과는 아닙니다.
- 상권 5건, 건축물대장 5건, 건설업 등록공시 5건은 양산의 샘플이며 전체 데이터가 아닙니다.
- 방문자수 5건은 2025-01-01 조회 첫 페이지로 종로구·중구 자료입니다. 고창·양산 방문 수요로 표시하면 안 됩니다. 원본의 현지인·외지인 등 방문자 구분을 그대로 보존했습니다.
- 관광자원통계는 아직 확보하지 못해 실제 테이블과 적재 데이터를 추가하지 않았습니다.

## 자료형과 결측값

| 데이터 | 저장 규칙 |
|---|---|
| 기본키·FK | INTEGER |
| 주소·업종명·메모 | TEXT |
| 행정코드·사업자번호·전화번호·지번 | TEXT, 앞자리 0 보존 |
| 면적·방문자 수 | NUMERIC, 소수 허용 |
| 날짜 | TEXT, 확인 가능한 날짜는 YYYY-MM-DD |
| 연도만 있는 사용승인 값 | approval_year, 원문은 approval_date_raw |
| 없는 값 | NULL, 임의로 0을 채우지 않음 |
| 원본의 0 | 0 그대로 보존. 실제 0인지 미상 표기인지 해석 검증 필요 |
| 원본 전체 행 | raw_records.payload_json에 보존 |

원본 빈집의 행 번호는 이번 스냅샷 안에서만 식별값입니다. 다음 해 CSV에서 행 순서가 달라질 수 있으므로 자동 갱신 시 같은 집이라고 단정해 덮어쓰면 안 됩니다. 현재 빌더는 기존 DB 덮어쓰기를 막습니다. 운영 시에는 자료 버전·수집 실행 기록과 안정적인 빈집 식별·변경 이력을 추가해야 합니다.

`saved_houses.updated_at`은 처음 생성될 때만 기본값이 설정됩니다. 메모를 변경하는 서버 코드에서 `updated_at=CURRENT_TIMESTAMP`도 함께 갱신해야 합니다. SQLite 연결마다 `PRAGMA foreign_keys=ON`을 실행해야 외래키 검사가 적용됩니다. 인증키는 DB에 넣지 않았습니다.

## 파일 사용 방법

- `빈집프로젝트.sqlite3`: 데이터가 들어 있는 실제 DB 파일.
- `schema.sql`: 테이블·관계·제약조건·인덱스 생성 SQL.
- `seeded_database.sql`: 실제 데이터까지 포함한 SQLite 복원 SQL.
- `테이블정의서.csv`: 13개 테이블의 모든 컬럼·자료형·기본키·필수 여부.
- `ERD.md`: 관계도. Mermaid를 지원하는 미리보기에서 표시됩니다.
- `조회예제.sql`: 지역별 빈집·관심 목록 등의 조회 예시.
- `검증결과.json`: 적재 건수·무결성·제약조건 검사 결과.

VS Code에서 DB 파일을 직접 표로 보려면 SQLite 뷰어가 필요합니다. 확장 프로그램 없이도 아래 Python 예제로 조회할 수 있습니다. 먼저 터미널의 현재 폴더를 프로젝트 루트로 맞추세요.

```python
import sqlite3
db = sqlite3.connect('database/빈집프로젝트.sqlite3')
db.execute('PRAGMA foreign_keys=ON')
for row in db.execute('SELECT id, address_public, grade FROM vacant_houses LIMIT 10'):
    print(row)
db.close()
```

## 검증

SQLite integrity_check와 foreign_key_check를 통과했습니다. 관심 저장 중복, 별점 6점, 존재하지 않는 빈집 참조가 실제로 거절되는 것도 확인했습니다. 검증용 회원과 저장 항목은 롤백하여 최종 DB에는 남기지 않았습니다.

월요일 설명에서는 **원본 보존 → 빈집 896건 정제 → 지역 기반 외부 데이터 연결 → 회원별 저장과 메모** 순서로 소개하면 됩니다. 현재 DB는 설계 확인용 시제품이며 전체 API 수집과 운영 서버 구성까지 완료된 상태는 아닙니다.
